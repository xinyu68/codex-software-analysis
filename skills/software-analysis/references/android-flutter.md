# Android 与 Flutter 路线

1. 记录 APK 来源、摘要、包名、版本、ABI 和 Manifest。静态 APK 检查依赖兼容的 JADX 与完整 JDK，不等于签名验证或实际运行。
2. 根据目录和库确定 Java/Kotlin、Flutter 或其他 native 业务边界。Flutter 的 `libapp.so` / `libflutter.so`、Dart snapshot hash、ABI 与 engine provenance 是选择后续工具的重要输入。
3. 按具体功能追踪代码。Java 层的 widget、通知或分享接口可能与 App 首页使用不同入口。不要凭方法名将二者视为同一接口。
4. 如果确实需要 Dart AOT 深入分析，检查对应版本和 ABI 是否被工具支持。Blutter 等工具是可选依赖，本插件不包含它们，也不承诺全部版本/平台可用。
5. 实际运行需要用户当前任务包含运行验证。复用当前 REA 的 ADB 工具或合适的设备能力；指定准确设备序列号和包名，避免操作用户另一台手机。新模拟器使用单独 AVD，避免继承旧案例的应用数据和会话。
6. 页面截图、时间、原始报价与计算值一起核对。静态发现的默认费率/差额不能当作永久不变的服务端配置。

ADB 服务、模拟器、instrumentation 与临时文件必须有所有权和回收记录。仅读取设备状态也可能触发 ADB 自启动，操作前了解当前客户端的实际行为。结束时只停止本次拥有的实例，不使用进程名称批量终止。

本版工作台提供 SDK 文件存在性检查和证据管理，设备操作复用 REA；没有自行下载系统镜像、创建 AVD 或启动模拟器的 MCP 工具。
